# 자율 디버깅 루프 — 상세

`/ait:debug` §6(관측 → 가설 → 최소 수정 → 재검증)의 상세다. 한 바퀴를 어떻게 도는지만
필요하면 SKILL.md §6의 요약으로 충분하다 — 아래는 관측 수단이 부족할 때의 degrade,
탈출 조건 판정, 루프가 건드려도 되는 범위를 더 정확히 알아야 할 때 읽는다.

## 1. 사이클 한 바퀴

1. **관측** — 증상을 재현하고, 그 순간의 상태를 아래 §2의 입력에서 모은다.
2. **가설 1개** — 반증 가능한 형태로 적는다("X가 Y라서 Z가 안 된다. X를 보면 확인된다").
   여러 개가 떠오르면 가장 싸게 반증되는 것부터 하나만 고른다.
3. **최소 수정** — 그 가설 하나만 흔드는 변경 하나(§3).
4. **재검증** — 원 증상 재현 절차를 그대로 다시 밟고, 2단계에서 지목한 관측 지점을 다시 본다.
5. **판정** — 통과면 종료, 실패면 수정을 되돌리고 다음 가설로. 판정 근거는 §6 형식으로 남긴다.

## 2. 관측 입력 — 환경별

| 환경 | 관측 수단 | 에이전트가 직접 취득 | 수단이 없을 때 (degrade) |
|---|---|---|---|
| 1 | devtools panel 탭(`references/panel-tabs.md`) | 아니오 — 어느 탭의 무엇을 볼지 지정하고 사용자 관측 결과를 받는다 | 패널 미설치면 `/ait:inject-devtools` 안내 후 브라우저 기본 DevTools만으로 진행 |
| 1 | 브라우저 콘솔·Network·예외 스택 | Playwright MCP가 붙어 있으면 일부(`browser_evaluate`), 아니면 아니오 | 에이전트가 콘솔에 붙여넣을 스니펫을 인쇄하고 사용자가 출력을 붙여넣는다 — 루프는 계속 돈다(관측 단계만 사람 경유) |
| 1 | `window.__ait?.state` (mock 런타임 상태) | Playwright MCP `browser_evaluate`로 읽음 | 위와 동일한 붙여넣기 경로 |
| 1 | 백그라운드 dev 서버 출력(빌드 에러·HMR 로그) | 예 | — |
| 1·3 | 프로젝트 소스·테스트 파일 | 예 (`Read`/`Grep`) | — |
| 3 | attach 후 도구 13종(`references/attach-tools.md`) | 예 — attach가 완료된 세션에서 | `ait-devtools` MCP 미배선이면 환경 3 관측 자체가 불가. `/ait:setup-debugger`를 안내하고, 그 전까지는 환경 1 안에서만 루프를 돈다 |
| 3 | `run_tests` 실기기 실행 결과 | 예 | 테스트 파일이 없으면 재현 절차를 수동으로 반복 |
| 3 | `list_pages`·`get_debug_status`(attach·relay 상태) | 예 | — |

**degrade 원칙은 기존과 같다** — MCP가 없으면 루프를 포기하는 게 아니라, 그 관측 단계만
사용자에게 스니펫/확인 요청으로 넘기고 나머지 단계(가설·수정·판정)는 에이전트가 계속 든다.
관측을 사람이 대신한 단계는 §6 로그에 그렇게 표시한다.

## 3. 수정 최소화 — 한 번에 한 변수

- **한 사이클에 논리 변경 하나.** 후보가 둘이면 사이클을 둘로 나눈다.
- **실패한 수정은 다음 사이클 전에 되돌린다.** 누적하면 어느 변경이 원인인지 판별할 수 없어
  루프 자체가 무의미해진다.
- **관측용 임시 계측**(임시 `console.log`, 임시 상태 덤프)은 루프 안에서 허용한다. 단 루프
  종료 시 전부 제거하고, 제거했다는 사실을 요약에 적는다.
- **리팩터링·포매팅·무관 파일 정리는 루프 밖.** 증상과 무관한 개선이 눈에 띄면 요약에 적고
  넘어간다.
- **의존성 추가·버전 변경은 루프 밖.** 그게 가설이면 수정 전에 사용자 확인을 받는다.
- **재검증은 원 증상 재현 절차 그대로.** 다른 경로로 동작을 확인한 것을 "고쳤다"로 판정하지
  않는다.

## 4. 탈출 조건

| 상황 | 처리 |
|---|---|
| 재검증 통과 | 루프 종료. §6 형식으로 요약(가설·수정·근거·임시 계측 제거 여부)을 인쇄한다 |
| **같은 가설이 2회 실패** | 즉시 중단하고 사용자 확인. 관측 요약 + 다음 후보 2~3개를 제시한다. 같은 가설로 3번째 시도는 하지 않는다 |
| **증상이 재현되지 않음** | 수정 금지. 재현 확보가 선행이다 — 입력·상태·경로를 특정해 재현 절차를 확정하기 전에는 소스를 고치지 않는다(재현 없이 고치면 재검증 자체가 불가능하다) |
| 서로 다른 가설 3개가 연속 기각, 또는 사이클 5회 초과 | hand-off. 지금까지의 관측·기각 근거를 정리해 넘기고, 환경 승급(1 → 3)이 필요한지 함께 제시한다 |
| 환경 1에서 재현 안 되고 실 SDK·네이티브 브리지가 의심됨 | 루프를 환경 3으로 옮긴다(SKILL.md 5-B → 5-C). mock 기준으로 단정하지 않는다 |
| 콘솔 상태 변경이 필요해 보임 | 루프 밖. 사용자 승인 없이는 진행하지 않는다(§5) |

## 5. 루프 경계 — 무엇을 건드려도 되는가

**허용** (사용자 확인 없이 루프 안에서):

- 미니앱 소스 편집(가설 하나를 흔드는 최소 변경), 임시 계측 추가·제거
- dev 서버 재기동, HMR 반영 대기
- 로컬 테스트·`run_tests` 실행, `ait build` 재빌드

**금지** (사용자 명시 승인 없이는 하지 않는다):

- 검수 제출(`review_*`·`bundle_submit_review`), 릴리즈·롤백, 프로모션, 푸시 발송 — 비가역이거나
  실사용자에게 노출되는 전환은 디버깅 루프의 일이 아니다
- 그 밖의 콘솔 상태 변이 도구 일반
- 의존성 추가·버전 변경, git commit·push

**예외 1건**: SKILL.md 5-B의 candidate 등록·업로드(`miniapp_create` → `bundle_upload` →
`bundle_upload_complete`)는 환경 3 진입에 필요하므로 디버깅 목적에 한해 허용한다 — 그것도
사용자가 환경 3 승급에 동의한 뒤에 한다. 이 예외는 검수 제출과 다르다(SKILL.md Out of scope).

## 6. 사이클 로그 형식

각 사이클을 이 형태로 한 번씩 인쇄한다 — 사용자가 루프를 따라올 수 있어야 하고, hand-off
시점에 그대로 인수인계 자료가 된다.

```
[사이클 2/5] 환경 1
증상: 로그인 버튼을 눌러도 authorizationCode가 안 옴
가설: appLogin() mock이 권한 미승인 상태에서 reject되는데 호출부가 catch를 삼킨다
관측: window.__ait?.state 의 권한 필드 (Playwright browser_evaluate)
수정: src/pages/Login.tsx 의 catch 블록에서 에러를 콘솔로 노출 (1파일, 임시 계측)
재검증: 로그인 버튼 재클릭 -> 콘솔에 mock reject 사유 출력됨
판정: 가설 성립 - 다음 사이클에서 권한 요청 선행 호출을 추가해 본검증
```

## 7. 예시 — 한 바퀴 (환경 1)

1. 사용자가 "메뉴에서 뒤로 스와이프하면 앱이 꺼진다"고 말한다.
2. 재현 확보: 어느 화면에서 몇 번째 진입인지 특정한다. 재현이 안 되면 여기서 멈추고
   재현 절차부터 맞춘다(§4).
3. 가설: 라우팅이 replace라 `window.history.length`가 안 쌓여 native swipe가 미니앱 종료로 빠진다.
4. 관측: `browser_evaluate`로 `window.history.length`를 메뉴 진입 전후로 읽는다.
5. 최소 수정: 그 한 라우팅 호출만 push로 바꾼다(다른 라우팅은 건드리지 않는다).
6. 재검증: 같은 경로로 진입 후 스와이프 — 종료되지 않으면 통과, 되면 되돌리고 다음 가설
   (예: gesture 설정 축)로 넘어간다. 브라우저에서 끝내 재현되지 않으면 환경 3으로 올라간다.

SDK API의 기대 동작이 애매해서 가설을 못 세우겠으면 docs MCP(`searchDocumentation`/`getPage`)로
해당 API 문서를 먼저 확인한다 — 추측으로 사이클을 태우지 않는다.
