# 아이데이션 절차 (발산 → 실현성 필터 → 수렴)

`/ait:plan`의 모드 판정(SKILL.md "입력" 절)에서 **모드 A**(아이디어가 막연함)로 판정됐을 때만 쓴다.
목표는 "재미있는 아이디어 찾기"가 아니라 **PRD 디스커션을 시작할 수 있는 후보
1개**를 30분 안에 만드는 것이다.

에이전트가 혼자 10개를 지어내고 고르지 않는다 — 발산은 사용자의 재료로 하고,
에이전트는 축을 제시하고 정리·필터링을 맡는다.

## 1. 발산 — 축 3개로 후보 모으기

한 번에 하나씩 묻는다. 각 축에서 2~4개, 합쳐서 **6개 이상** 모이면 충분하다.
이 단계에서는 실현성·수익성을 평가하지 않는다(평가는 2단계).

| 축 | 질문 | 나오는 것 |
|---|---|---|
| 불편 | "최근 한 달 안에 스마트폰으로 처리하다 번거로웠던 일이 있나요?" | 문제 기반 후보 |
| 반복 | "종이·엑셀·단톡방으로 반복해서 관리하는 게 있나요?" | 디지털화 후보 |
| 역발상 | SDK 도메인 카탈로그에서 2~3개를 제시하고 "이걸 쓰면 뭐가 편해질까요?" | 능력 기반 후보 |

역발상 축에서 제시하기 좋은 도메인: `location`(현장에서만 되는 것),
`camera`(찍으면 끝나는 것), `contacts`(사람과 엮이는 것), `iap`/`ads`(수익
모델이 명확한 것), `notification`(다시 돌아오게 하는 것).

후보는 한 줄로 적는다 — `<누가> <언제> <무엇을> 한다`.
예: "동호회 총무가 모임 당일에 참석자를 체크한다."

## 2. 실현성 필터 — 미니앱 제약으로 후보를 깎는다

각 후보에 아래 6개 질문을 적용한다. **하나라도 ✗면 후보를 버리거나 범위를 줄인다.**

1. **웹으로 되는가** — 미니앱은 토스 앱 WebView에서 도는 웹(React DOM) 앱이다.
   백그라운드 상시 실행, 시스템 전역 접근처럼 네이티브 앱이라야 되는 기능이
   핵심이면 성립하지 않는다.
2. **SDK 카탈로그 안에 있는가** — 필요한 기기 능력이 SKILL.md의 도메인 18개
   안에 있는가. 밖이면 그 기능은 없는 셈 치고 후보를 다시 쓴다.
   (`iframe`으로 외부 서비스를 얹어 우회하는 설계는 쓰지 않는다 — 보안 심사에서
   반려된다. 확인은 docs MCP `searchDocumentation({query: "iframe"})`.)
3. **서버 없이 v1이 되는가** — harness는 클라이언트 축만 다룬다. 서버가 있어야만
   의미가 생기는 아이디어면, v1을 로컬 저장(`storage`)만으로 성립하는 범위로
   줄이거나 백엔드를 직접 준비해야 한다는 것을 명시한다.
4. **한 화면에서 가치가 나는가** — 미니앱 진입은 짧고 단발이다. 첫 화면에서
   "뭘 하는 앱인지 + 핵심 행동 1개"가 끝나지 않으면 범위를 줄인다.
5. **검수를 통과할 수 있는가** — 출시 검수는 서비스·기능·디자인·보안 4축으로
   본다. 카테고리(게임/비게임)에 따라 출시 가이드가 갈리고, 실제 서비스와 다른
   카테고리를 고르면 검토 단계에서 조정 안내를 받는다. 사행성·과장 프로모션,
   금융 오인 소지가 있는 표현은 후보 단계에서 뺀다.
6. **권한을 거부해도 쓸모가 있는가** — 위치·카메라·연락처는 사용자가 거부할 수
   있다. 거부 시 앱이 아무것도 못 하면 그 후보는 권한 의존도를 낮춰야 한다.

필터 결과는 표로 정리해 사용자에게 보여준다 — 왜 떨어졌는지가 다음 후보의
재료가 된다.

## 3. 수렴 — 후보 1개 선택

남은 후보가 2개 이상이면 아래 순서로 자른다.

1. **데모 테스트**: "이 앱을 30초 안에 보여준다면 무엇을 보여줄 것인가?"에
   답이 안 나오는 후보를 버린다.
2. **최소 도메인**: 필요한 SDK 도메인이 적은 쪽을 남긴다(첫 미니앱일수록).
3. **사용자 선택**: 그래도 남으면 사용자에게 고르게 한다 — 에이전트가 임의로
   정하지 않는다.

선택된 후보를 한 줄 정의로 다시 쓰고, 곧바로 PRD 디스커션(SKILL.md 3단계)으로
넘어간다.

## 하지 말아야 할 것

- ❌ 사용자에게 묻지 않고 아이디어 10개를 지어내 그중 하나를 고르기.
- ❌ 실현성 필터를 건너뛰고 후보를 PRD로 넘기기 — 필터 없는 후보는 PRD 중반에
  무너진다.
- ❌ 시장 규모·수익 추정 같은 근거 없는 숫자 만들기.
- ❌ 실존 서비스의 이름·화면을 그대로 베끼는 후보를 권하기.
- ❌ 문서로 확인하지 않은 SDK 기능을 "된다"고 전제하기 — 불확실하면 docs MCP로
  확인하거나 "확인 필요"로 남긴다.
