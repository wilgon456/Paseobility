# 요청 무게 · 리스크 점검 · 화면 명세 (build mode)

화면을 그리기 전에 design이 거치는 단계다. 쓰는 사람은 개인 바이브코더부터
제작사·제휴사까지 다양하고, 디자인 전문가가 아닐 수 있다. "토스처럼 만들라"고
강요하지 않는다 — **전문 디자이너 대신, 제작자가 놓치기 쉬운 걸 대신 짚어주는
도우미**다.

두 단계를 한 흐름으로 돌린다:

1. **리스크 점검**(필수, 가볍게) — 이대로 만들면 검수에서 걸리거나 유저가
   싫어할 소지가 있는지 본다. 없으면 조용히 통과, 있을 때만 짚는다.
2. **화면 명세** — 무엇을 어떤 순서로 배치하고 각 요소에 무슨 내용이 들어가는지
   컴포넌트+콘텐츠 단위로 적는다. 실제 그림은 `render-rules.md`가 그린다.

## 언제 무겁게, 언제 가볍게 — 요청 무게 판별

들어온 요청의 **성격**을 먼저 본다. "리스크 분석 할까요?"라고 묻지 않는다.
판별은 요청 길이가 아니라 성격이다.

| 요청 성격 | 신호 | 처리 |
|---|---|---|
| 국소 수정 | 특정 요소/화면을 지목 + "바꿔/나눠/추가/옮겨", 기존 화면 전제 | 리스크 점검 생략. 뭘 바꾸는지 한 줄 확인 → 바로 명세 |
| 명세 완료형 | 신규지만 요청이 화면 구성을 구현 수준으로 다 적어옴(레이아웃·요소·문구·데이터까지) | 리스크 점검은 가볍게(눈에 걸리는 것만), 명세는 요청 그대로. 없는 문제를 지어내지 않는다 |
| 방향 탐색 | "이 기능 화면 어떻게 만들지?", 방향이 모호 | 리스크 점검 + 명세 둘 다. 명세는 1~2안 |
| 신규 설계 | "만들어줘" + 화면/플로우가 열려 있음 | 리스크 점검 + 명세 둘 다. 명세는 1~2안 |

**명세 완료형 판별 팁**: 요청에서 "문제"를 뽑았는데 그게 *요청에 이미 적힌
주의사항*이면(예: 요청에 "자동 갱신 안 된다고 안내"라고 써 있는데 그걸
"자동 vs 수동 문제"로 재라벨링), 그건 문제가 아니라 명세다 — 지어내지 말고
그대로 그린다.

## 리스크 점검 (가볍게, 없으면 조용히)

만들려는 화면·기능을 아래 4가지로 훑는다. **핵심 원칙은 "가볍게, 없으면
조용히 통과"다.** 문제가 안 보이는 요청에 억지로 리스크를 만들어내지 않는다.
걸리는 게 있을 때만, 걸린 것만 짚는다. 4개를 매번 다 채우려 하지 않는다.
짚을 땐 **단정하지 않는다** — "이대로면 검수에서 걸릴 수 있어요" 톤으로,
제작자가 판단할 여지를 남긴다.

| 항목 | 무엇을 보나 |
|---|---|
| ① 검수 반려 리스크 | 검수에서 반려되거나 노출이 제한될 소지 — 존엄·혐오, 외모·조건 서열화, 제3자 정보 노출, 자극·사행, 오해 소지. 아래 상세 렌즈로 본다 |
| ② 핵심 가치 매몰 | 이 앱의 진짜 가치가 첫 화면에 드러나는가 — 가치를 보여주기 전에 로그인을 강요하지 않는지, 첫 화면이 텍스트만이라 무슨 앱인지 이해가 안 되지 않는지, 입력만 시키고 가치가 약하지 않은지(소프트) |
| ③ 다크패턴 | 예상치 못한 광고, 가짜 버튼, 이탈을 막는 강제 유도, 거절 경로 없음 등 |
| ④ 광고 정직성 | 광고·프로모션·혜택·추천 접점이 있으면 아래 5축 렌즈로 본다 |

①은 검수 통과 여부, ②③④는 유저가 이 앱을 다시 쓸지를 가른다.

### 검수 반려 리스크 — 상세 렌즈

**핵심 원칙: 표현 하나하나가 아니라 "화면 전체가 유저에게 어떻게 읽히나"로
본다.** 제작자의 의도가 선해도 판단 기준은 받아들이는 유저의 해석이다.

| 리스크 | 무엇을 보나 |
|---|---|
| 존엄·혐오 | 특정 개인·집단의 존엄을 해치거나 비하·조롱하는가 |
| 외모·신체·조건 서열화 | 외모·나이·체형·연봉·조건을 점수화·등급화해 줄 세우는가 |
| 제3자 정보 노출·사찰 | 당사자 동의 없이 타인의 정보를 분석·노출·평가하는가 |
| 자극·사행·악용 | 과도하게 자극적인 콘텐츠, 사행성, 익명 괴롭힘 등 |
| 오해 소지 | 토스 공식으로 오인하게 하거나, 의료·법률·금융을 실제 상담·조언으로 오인시키는가 |

단정하지 말고 "이대로면 검수에서 걸릴 수 있어요"로 짚어 제작자가 판단하게
한다. 목적은 검수 통과가 아니라 유저에게 해가 안 되는 것이다.

### 광고 정직성 — 광고 가치화 5축 렌즈

**전제: 광고는 무조건 나쁜 게 아니다.** 이 렌즈의 목표는 "광고티를 지우는
것(위장)"이 **아니라** "광고 자체를 유저가 가치 있게 느끼는 경험으로 만드는
것"이다.

| 축 | 질문 | 없으면 생기는 거부감 |
|---|---|---|
| 관련성 | 이 유저·이 순간에 진짜 맞는 제안인가 | 엉뚱한 광고 = 거부감 1순위 |
| 보상 | 참여하면 무슨 실익? "내가 이득 본다"는 심상이 있나 | 주는 것 없이 시간만 뺏김 |
| 자기표현 | 공유·참여가 유저를 돋보이게 하나 | "내가 광고하는 사람"이 되기 싫음 |
| 재미 | 그 자체로 즐거운 콘텐츠·인터랙션인가 | 지루한 강매 |
| 정직함 | 광고임을 숨기지 않되 당당히 가치를 제시하나 | 속았다는 배신감 |

**정직함이 상위다.** 관련성 없는 강매, 기만, 사행성 과장은 광고 가치화가
아니라 착취다 — 유저를 속이지 않는다는 바닥 규칙이다.

### UX 휴리스틱 셀프 체크 (강제 아님, 걸리면 짚기)

위 4항이 "터지는 리스크"라면, 아래 넷은 "더 나으면 좋은" 품질 휴리스틱이다.
강하게 강제하지 말고, 걸리는 게 있으면 개선 여지로만 짚는다.

| 렌즈 | 체크 질문 |
|---|---|
| 정보 밀도 | 이 화면에 목표가 하나로 뚜렷한가? 더 뺄 수 있는데 넣은 건 없나? |
| 문구 직관성 | 글을 다 안 읽어도 다음 행동을 알 수 있나? 가치를 모르는데 입력·비용부터 요구하지 않나? |
| 행동 유도 | 왜 이걸 해야 하는지 이유가 보이나? 플로우가 한 맥락으로 이어지나? |
| 인지·노동 비용 | 각 단계 질문에 3초 안에 답할 수 있나? 타이핑을 탭·선택으로 줄일 수 있나? |

## 화면 명세

무엇을 그릴지를 **화면별 컴포넌트 + 콘텐츠 명세**로 적는다. 실제 컴포넌트·
수치·색은 렌더 단계(`render-rules.md`)가 정하므로, 명세는 구체적이되
**치수·아이콘 파일명·CSS는 비운다.**

### 발산은 1~2안

제작자는 보통 "뭘 만들지"를 이미 정하고 온다.

- **기본안 1개**를 기본으로 한다 — 요청을 가장 직접 푸는 형태.
- 요청이 열려 있거나 더 나은 대안이 뚜렷하면 **재정의안 1개**를 곁들인다.
  최대 2안.
- 국소 수정·명세 완료형은 **1안만.**

### 명세에 쓰는 것 / 안 쓰는 것

| 쓴다 (O) | 안 쓴다 (X) |
|---|---|
| 컴포넌트 타입(타이틀, 검색 필드, 목록, 카드, 배너, 버튼, 칩, 탭 등) | 특정 컴포넌트명·아이콘 파일명 |
| 담기는 콘텐츠와 예시 데이터 | 치수(px) — 폭·높이·패딩·폰트 크기 전부 |
| 배치 관계(최상단/그 아래/오른쪽/좌우 분할) | 색값·CSS·렌더 규칙 |
| 반복 요소의 개수 | 인터랙션 코딩 디테일(호버 hex, 애니메이션 ms) |
| 각 화면의 핵심 정보 1개 | 개발 스펙(API, 상태관리) |

**예시 데이터는 오히려 적극 쓴다.** "오늘 방문 3명", "이번 달 적립 1,200P"
같은 구체 예시는 렌더 단계가 정확히 그리게 돕는다.

### 세 가지 필수 정리 규칙

1. **수치를 쓰지 않는다.** 크기가 중요하면 px 대신 위계 언어("가장 크게",
   "작게", "시각적 1순위")로 쓴다.
2. **아이콘 파일명·CSS·렌더 규칙을 쓰지 않는다.** 렌더 단계(`render-rules.md`)
   가 정한다.
3. **둘 중 하나로 열어두지 않는다.** 맥락에 맞는 하나로 결정해서 명세한다.

## 플로우는 메인 한 컷에서 멈추지 않는다

여러 화면이 이어지는 플로우면, 메인 화면 하나만 그리고 끝내지 않는다.

- 완료성 액션(결제·가입·신청 등)이 끝에 있으면 **완료 화면**을 자동으로
  포함한다.
- 공유·초대가 있으면 "공유받은 사람이 들어오는 화면"이 필수.
- 빈 상태, 에러, 재방문 같은 변형은 **별도 화면**으로 뺀다.

## 넘기기 전 체크리스트

- [ ] 화면 단위로 분리했나? 각 화면에 이름 + 한 줄 목적이 있나?
- [ ] 각 화면 컴포넌트를 위→아래(그리는 순서 = 읽는 순서)로 나열했나?
- [ ] 각 컴포넌트에 [타입] + [콘텐츠/예시 데이터]가 다 붙어 있나?
- [ ] 반복 요소의 개수를 박았나?
- [ ] 각 화면의 핵심 정보 1개를 표시했나?
- [ ] 상태/변형은 별도 화면으로 뺐나?
- [ ] 수치·아이콘명·CSS·either-or를 다 비웠나?

> **핵심 태도: 물음보다 초안이 먼저다.** 정보가 부족해도 상식적으로 추론해서
> 일단 명세를 만든다. 진짜 못 그리는 것만, 최대 2개까지 묻고 바로 진행한다.
> 한 번 물은 건 다시 묻지 않는다.

## 하지 않는 것

- 없는 리스크·문제를 지어내기(요청에 안 걸리면 조용히 통과)
- 이미 다 명세된 요청에 문제 재정의·발산을 강제하기
- 제작자에게 "토스처럼 만들라" 강요하기
- 구체적 수치·색값·아이콘 파일명·CSS 지정(→ `render-rules.md`)
- 명세를 either/or로 열어둔 채 넘기기
- 시각 디자인 퀄리티 판단(→ 렌더 단계)
